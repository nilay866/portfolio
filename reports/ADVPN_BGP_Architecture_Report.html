1. Executive Summary & Production Safety Guarantee

This audit encompasses the full configuration backups of 16 enterprise FortiGate firewalls running FortiOS 7.4.x (centered around FortiOS 7.4.12 on the central hub RND-200G). The objective is to verify whether dynamic Auto-Discovery VPN (ADVPN) with iBGP Route Reflection and SD-WAN steering is functioning properly across the enterprise, diagnose why communication is broken or incomplete between specific sites, and provide an exact, verified CLI remediation playbook that will guarantee full end-to-end communication without affecting any existing production traffic.

⚠ Current State: Why ADVPN Communication Is Fractured Today
While the central Hub (RND-200G) and 13 spokes have successfully established parent IPsec tunnels, end-to-end data communication and dynamic spoke-to-spoke shortcuts are failing or severely degraded due to seven primary defects:
  • Head Office (HO) is Completely Offline: All 6 overlay interfaces are administratively shut down (set status down), public gateway IPs contain syntax typos, BGP AS 65000 is unconfigured, and SD-WAN/firewall policies are completely missing.
  • Plant-West-01 Gateway IP Typo on WAN2: Tunnel H1T1S2 points to 203.0.113.0 (the subnet network address) instead of 203.0.113.1.
  • Address Group Drift Across Spokes: Outbound Firewall Policy 1000 and SD-WAN rules filter by BRANCH_NET_GROUP. Key spokes (e.g., Enterprise_USA, Tech_RND_02, Tech_RND_03, HO) are missing entries for Regional-North-01, Logistics-Hub-West, Plant-East-Alpha, and Plant-Central-01, resulting in silent packet drops.
  • Multi-LAN Interface Drops: Spokes with multiple internal subnets (e.g., Tech_RND_04 internal4 172.20.50.0/24 and Plant-Central-01 ports 2, 4, 5, 6) omit these interfaces from Policy 1000 source interfaces, dropping outbound traffic to other branches.
  • Subnet IP Overlap: Plant-Central-02 configured internal2 with 192.168.7.254/24, conflicting directly with Logistics-Hub-West (192.168.7.0/24).
  • Routing Distance Inversion with Legacy Tunnels: Existing legacy site-to-site IPsec tunnels have static routes with Distance 5 or 10. iBGP routes have Distance 200. The FIB always selects the legacy static route, preventing ADVPN from being utilized.
✔ The Non-Disruptive Production Guarantee
No legacy tunnels or internet breakouts will be disrupted. The remediation plan adheres to three strict non-disruptive principles:
  1. Zero Deletions: All existing address objects, legacy static routes, and legacy IPsec tunnels remain untouched during overlay initialization.
  2. Additive Group Expansion: BRANCH_NET_GROUP is updated strictly using FortiOS append member CLI commands, ensuring existing communication is never severed.
  3. Staged Distance Migration: Legacy static routes are not deleted; their administrative distance is gracefully modified to 210. Because iBGP operates at distance 200, ADVPN immediately takes precedence. If an ADVPN tunnel ever degrades, FortiOS automatically and instantaneously fails back to the legacy tunnel with zero packet loss.

Dynamic ADVPN Shortcut Signaling Mechanics (FortiOS 7.4.x)

FortiOS ADVPN relies on an automated control-plane signaling loop to dynamically establish shortcut tunnels between spokes without manual tunnel provisioning:

  1. Initial Path: Spoke A sends an initial packet towards Spoke B's LAN (e.g., 192.168.10.0/24). The packet is routed via the parent tunnel to the Hub.
  2. Redirect Trigger: When the Hub receives a packet on a tunnel with auto-discovery-forwarder enable and forwards it out another tunnel with the same network ID, the Hub generates an IKE redirect message to Spoke A.
  3. Resolution Query: Spoke A (configured with auto-discovery-receiver enable) intercepts the redirect and transmits an IKE resolution query through the Hub to Spoke B.
  4. Shortcut SA Negotiation: Spoke B receives the query and initiates a direct IKE Phase 1 and Phase 2 SA to Spoke A's public IP.
  5. FIB Route Installation: Upon tunnel establishment, FortiOS automatically installs a dynamic kernel shortcut route pointing directly to the new shortcut interface. Subsequent traffic flows directly spoke-to-spoke, completely bypassing the Hub.
  6. Hub Offload Requirement: Crucially, Hub Policy 194 is configured with auto-asic-offload disable and np-acceleration disable. In FortiOS 7.4.x, offloading the initial packet to NPU hardware prevents the CPU from inspecting the forwarded packet, which inhibits the generation of IKE redirect messages. Disabling ASIC offload on the Hub branch-to-branch policy guarantees that shortcut signaling triggers reliably.

4. Detailed Technical Analysis of the 7 Root Causes

Root Cause 1: Head Office (HO) Total Inactivity & Configuration Blunders

The Head Office firewall (HQ_Core_Gateway.conf) is the most severely impaired device in the entire deployment. Despite having phase 1 and phase 2 definitions created, it is 100% unable to participate in ADVPN or establish communication due to four fatal flaws:

  • Administrative Shutdown: Under config system interface, all 6 overlay interfaces (HUB1-VPN1, HUB1-VPN2, HUB1-VPN3, H1T1S2, H1T2S2, H1T3S2) have set status down explicitly configured. FortiOS will not attempt IKE negotiation while an interface is down.
  • Public Gateway IP Truncation:
    • HUB1-VPN1: Configured with set remote-gw 203.0.113.9 (missing the trailing 8; actual Hub IP is 203.0.113.1).
    • HUB1-VPN2: Configured with set remote-gw 198.51.100.13 (missing the trailing 0; actual Hub IP is 198.51.100.1).
  • ADVPN Parameters Missing on Overlay 3: HUB1-VPN3 is missing set auto-discovery-receiver enable, set network-id 3, and set network-overlay enable.
  • Total BGP Absence: Under config router bgp, there is no Autonomous System (set as 65000) and no Router ID (set router-id 10.240.0.22). Although neighbor statements exist, the BGP daemon remains dormant.
  • Missing SD-WAN Zone & Firewall Policies: HO lacks the To_HUB SD-WAN zone and has no overlay policies (Policy 1000, 1001, 1002). Even if the tunnels were to negotiate, all packets would be dropped by the implicit deny rule.

Root Cause 2: Plant-West-01 Phase 1 Remote Gateway Typo on WAN2

On Plant_West_01.conf, tunnel H1T1S2 is configured with:

config vpn ipsec phase1-interface edit "H1T1S2" set remote-gw 203.0.113.0 # FAILS: 203.0.113.0 is the network address of the /29 subnet! next end

The correct gateway IP is 203.0.113.1. Because of this typo, IKE packets sent over WAN2 are dropped upstream, cutting Plant-West-01's WAN2 overlay redundancy in half.

Root Cause 3: Address Group Asymmetry & Drift in BRANCH_NET_GROUP

On the Spokes, firewall policies and SD-WAN steering rules enforce strict destination matching:

config firewall policy edit 1000 set name "BRANCH---->HUB" set srcintf "internal" set dstintf "To_HUB" set dstaddr "BRANCH_NET_GROUP" set action accept next end

While recent spokes like Commercial-Hub-East and Plant-North-Beta contain 43 member address objects in their group, older spokes like Enterprise_USA, Tech_RND_02, and Tech_RND_03 only contain 31 objects. Crucial spoke subnets are missing:

  • Regional_North_01_LAN (192.168.10.0/24)
  • Logistics_Hub_West_LAN (192.168.7.0/24)
  • Plant_East_172.23.0.0 (172.23.0.0/24)
  • Plant_Central_172.28.0.0 (172.28.0.0/24)
  • Indoor_Lan_172.25.0.0 (172.25.0.0/24)

Consequence: When a user at Tech_RND_02 or Enterprise_USA attempts to send traffic to Regional-North-01 or Logistics-Hub-West, the packet arrives at the FortiGate firewall engine, fails to match Policy 1000 because the destination IP is not in BRANCH_NET_GROUP, and is silently dropped by the implicit deny rule (Policy 0).

Root Cause 4: Multi-LAN Spokes Omitted from Ingress Policy

Several spokes have multiple internal LAN interfaces, but only a single LAN interface is bound to Policy 1000:

  • Tech_RND_04: Has three local subnets: internal (10.191.50.0/24), internal1 (192.168.50.0/24), and internal4 (172.20.50.0/24). Policy 1000 only lists srcintf "internal" "internal1". All outbound traffic from internal4 (Server Zone) is dropped.
  • Plant-Central-01: Has six local subnets (ports 1, 2, 3, 4, 5, 6). Policy 1000 only lists srcintf "port1". Traffic originating from port2 (10.101.8.0/22), port4 (10.104.8.0/22), port5 (192.168.28.0/22), and port6 (172.28.0.0/24) is dropped.

Root Cause 5: Overlapping Subnet IP Collision

A direct IP address collision exists between two branch offices:

  • Logistics-Hub-West: Configured on internal with 192.168.7.10/24 and advertises 192.168.7.0/24 into iBGP.
  • Plant-Central-02: Configured on internal2 with 192.168.7.254/24 and advertises 192.168.7.0/24 into iBGP.

When both branches advertise 192.168.7.0/24 to the Hub Route Reflector, BGP installs ambiguous ECMP or nondeterministic routes, causing asymmetric packet routing and connection timeouts.

Root Cause 6: Routing Distance Conflict with Legacy Tunnels

Most spokes have legacy point-to-point IPsec tunnels with static routes configured at Administrative Distance 5 or 10:

config router static edit 12 set dst 10.191.12.0 255.255.255.0 set device "RND_Legacy_Tunnel" set distance 10 # Wins over iBGP distance 200! next end

Because iBGP routes have Distance 200, the FortiOS Forwarding Information Base (FIB) always selects the legacy static route. The ADVPN overlay path is never utilized.

Root Cause 7: Missing Overlay Health-Checks in SD-WAN

Spokes currently probe public DNS (8.8.8.8) over their physical WAN interfaces, but have no SD-WAN performance SLA health-check targeting the Hub Loopback (10.240.0.1) over the overlay tunnels. Without an overlay SLA, FortiOS cannot dynamically detect tunnel blackholes or steer traffic to the best overlay path.
